# Runbook: Config and Secret Drift

When the value a pod is running with no longer matches the value the rest
of the world expects. Covers incident scenarios 07 and 08.

Two properties make this failure mode distinctive, and both are worth being
able to state out loud:

1. **The change and the failure happen at different times.** `envFrom`
   values are read once, when the container starts. Edit a ConfigMap or
   Secret and *nothing happens* -- the running pods keep the old values
   until something restarts them. The outage arrives with the next deploy,
   the next node recycle, or the next scale-up, which may be hours later
   and will look unrelated.
2. **The failure is usually `Ready`-shaped, not crash-shaped.** The process
   starts fine. It's the dependency check that fails, so pods sit `Running`
   and never `Ready` -- and `Running` is what most dashboards show you.

## Symptoms

- `kubectl get pods` shows `Running` with `0/1` in the READY column, no
  restarts, no crash loop.
- `kubectl get endpoints <app>-backend` is empty or short: unready pods are
  not in the Service, so the ALB won't route to them.
- A rollout that never completes, with old pods still serving on the old
  (working) values.
- Datadog: often **no monitor fires at all**. Error rate and p95 stay flat
  because the healthy old pods are absorbing all the traffic. What you
  have instead is the log line and the event.

## Diagnostic commands

The log message is the fastest route to a root cause here -- read it before
anything else.

```bash
# In Datadog:
#   service:<app>-backend status:error
#   source:kubernetes kube_namespace:<app>
# Or from a terminal:
kubectl -n <namespace> logs -l app=<app>-backend --tail=50

# Ask the pod directly what it thinks about its dependencies
kubectl -n <namespace> get pods
kubectl -n <namespace> port-forward <pod> 14000:4000 &
curl -s localhost:14000/readyz | jq .    # 503 + a "reason" string when unhappy
curl -s localhost:14000/healthz | jq .   # still 200 -- the process is fine

# Which values is the pod actually running with?
kubectl -n <namespace> exec <pod> -- printenv | grep -E "^(PORT|PG|DD_)"

# What do the objects say now?
kubectl -n <namespace> get configmap <app>-backend-config -o yaml
kubectl -n <namespace> get secret <app>-db-credentials -o jsonpath='{.data.PGUSER}' | base64 -d

# When did the objects last change, vs. when did the pods start?
kubectl -n <namespace> get configmap <app>-backend-config -o jsonpath='{.metadata.managedFields[*].time}'
kubectl -n <namespace> get pods -o wide --sort-by=.metadata.creationTimestamp
```

That `printenv` versus `get configmap` comparison is the whole diagnosis for
a drift incident: it shows you the two values that are supposed to be the
same and aren't.

## Reading the message

| Message | Meaning | Where the truth lives |
|---|---|---|
| `password authentication failed for user "<app>_app"` | The Secret's `PGPASSWORD` doesn't match the role's password on RDS | RDS. The Secret is the copy that drifted |
| `role "<app>_app" does not exist` | The Secret's `PGUSER` is wrong, or the database was rebuilt without the role | RDS |
| `database "<app>_db" does not exist` | Wrong `PGDATABASE`, or pointed at a different instance | RDS |
| `getaddrinfo ENOTFOUND` / `ECONNREFUSED` on `PGHOST` | Wrong host, or the RDS endpoint changed (a restore or a replacement gives you a new one) | Terraform output `rds_address` |
| `Readiness probe failed: ... connection refused`, with the app logging `listening on 4001` | The container listens on a port the probe doesn't check | `apps/<app>/k8s/deployment-backend.yaml` -- probes are hardcoded to 4000 |

## Fix

1. **Fix the object, then restart.** Patching alone changes nothing for
   running pods; restarting alone reloads the same bad value. You need
   both, in that order.
   ```bash
   # config drift
   kubectl -n <namespace> patch configmap <app>-backend-config -p '{"data":{"PORT":"4000"}}'
   kubectl -n <namespace> rollout restart deployment/<app>-backend

   # credential drift
   kubectl -n <namespace> patch secret <app>-db-credentials \
     -p '{"stringData":{"PGPASSWORD":"<the-real-password>"}}'
   kubectl -n <namespace> rollout restart deployment/<app>-backend
   ```
2. **`rollout undo` will not help.** The Deployment's pod template never
   changed -- only the object it references did. This is the single most
   common wrong first move on this failure mode.
3. If the real credential is genuinely lost: each app's database password
   is generated by `scripts/setup.sh` (`openssl rand`) and stored **only**
   in the Secret. There is no copy in Terraform state. Re-running
   `./scripts/setup.sh` generates a fresh password, `ALTER ROLE`s it on
   RDS, and re-applies the Secret -- that's the recovery path.
4. Confirm both layers recovered:
   ```bash
   kubectl -n <namespace> get pods            # 1/1 READY
   kubectl -n <namespace> get endpoints <app>-backend
   curl -s https://<app>.$(cat .lab-domain)/readyz
   ```

## Prevention

- Have one system of record per value, and generate the rest. Two hand-
  maintained copies of a password will drift; it is only a question of when.
- Make config changes visible where the incident will be investigated: a
  `kubectl patch` by hand leaves no trace in `git log` and none in
  `rollout history` either.
- Roll deliberately after a config change instead of waiting for the next
  restart to surface it. A failure you triggered at 15:00 on purpose is a
  ten-minute fix; the same failure surfacing at 03:00 during a node recycle
  is an incident.
- Alert on unavailable replicas, since this failure mode produces no error
  rate and no latency change to alert on (see
  [devops-vs-sre.md](../devops-vs-sre.md#the-detection-gap)).

## Reproduce this in the lab

```bash
scripts/chaos/break-config.sh <app>      # port drift: Running, never Ready, then crash loop
scripts/chaos/rotate-secret.sh <app>     # credential drift: Running, never Ready

scripts/chaos/break-config.sh <app> --undo
scripts/chaos/rotate-secret.sh <app> --undo
```
